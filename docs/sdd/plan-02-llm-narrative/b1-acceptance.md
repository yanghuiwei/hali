## 1. 为什么可以自动化（而不是「必须人工点击」）

原判断「只能人来跑」的前提是**界面状态从外部不可观测**。`HALI_DEBUG_LOG` 镜像（`be9cddc`）把叙事/面板/状态行/输入与按钮置灰状态全部镜像到 stdout（真实窗口下同样落进 `user://logs/godot.log`，已实测），于是验收变成：

- 探针真的实例化 `res://src/ui/main.tscn`；
- 通过**界面自己的处理器**（`_on_start_pressed` / `_on_command_submitted` / `_on_magic` / `_on_save` / `_on_load` / `_on_audit`）驱动，等同于点按钮/回车；
- 断言从**真实控件状态**（`world`、`status_label.text`、`command_edit.editable`、`button_row` 的 `disabled`）与**真实日志文本**（`RichTextLabel.get_parsed_text()`）读出；
- 全程 `HALI_DEBUG_LOG=1`，镜像原文同时留在 stdout 作为可复核证据。

与「人工点击」的差别只剩：没有真的 OS 鼠标/键盘事件、没有像素级渲染检查、没有真的关进程重开（用同进程**新实例**模拟）。这三条已登记为残余（§4）。

## 4. 残余（仍未覆盖，诚实登记）

1. **真实鼠标/键盘事件**未测：探针调用的是界面处理器本身（`text_submitted` / `pressed` 的同名槽），不是 OS 级事件注入。控件接线（`connect`）本身由代码静态可读 + 计划 01 Task 11 审查覆盖。
2. **像素级可读性**（面板排版、字号、滚动）未测：headless 无布局，`get_line_count()` 返回 0。如需，人工开窗看一眼即可。
3. **真的关进程重开**用「同进程新实例」代替（`_ready` 全流程重跑、只读存档，行为等价）。
4. **真机 LLM 的等待期**（几十秒、超时/断网降级）未测：用户裁定 **B2 暂不做**；本文件只覆盖「置灰/恢复」这一 UI 契约，用 mock 慢 provider 验证。
5. `§8#58`（等待期无超时/取消）与 `§8#62`（提交路径无失败恢复）**仍开放**——本条只是让「卡住」可观测，未修复。

## 5. 顺带产出

- **踩坑（已写入 `HANDOFF §4`）**：`RichTextLabel.text` **不会**被 `append_text()` 更新（实测读回空串），必须用 `get_parsed_text()`；headless 下 `get_line_count()` 恒为 0。生产代码目前没有读 `log_view.text` 的地方，所以不是线上缺陷，但会坑未来的观测工具。
- **§8#69 的硬证据**（哑炮却有学院）：本次实测哑炮 `house_id=gryffindor`（`bloodline_id=squib`），与正典「哑炮不进霍格沃茨」冲突；根因仍是 `character_creation.gd:175` 无条件 `assign_house()`。
- **§8#70 的硬证据**（创建界面 UX）：性别恒为「未定」（无输入控件）；姓名默认「无名者」可直接提交。本次探针显式填了姓名，故造出的是「测试哑炮·未定」。
- **练药递减的准确文案**：第三次为「你继续练魔药学，但收获不如从前（重复练习**收益**下降）」——含「收益下降」子串，与计划 Step 6 的预期一致。
